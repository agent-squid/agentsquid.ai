The model is not the agent

Ask which is the best model for coding and the conversation usually jumps straight to coding agents: Claude Code or Codex. But a model does not inspect your repository, choose tools, apply patches, manage context, or recover from a failed command by itself. A harness does that. What you experience as an “agent” is the combination.

agent = harness + model + project components + global components

So, does the harness make the difference? Yes—but not by the same amount for every model. With a frontier model, the gap between competent harnesses can feel surprisingly small. The model is capable enough to plan around rough edges, recover from weak tool calls, and infer missing instructions. Change the harness and you may improve speed, ergonomics, or token use without completely changing whether the task succeeds.

Move down to a mid-tier, free-tier, or local model and that answer changes. The harness stops being packaging and starts becoming leverage.

Smaller models expose the harness

A less capable model has less room for wasted motion. Vague tool descriptions, oversized context, noisy command output, and poor edit feedback consume a larger share of its attention. A strong harness narrows the next decision, presents the right evidence, and turns a large coding job into a sequence of tractable actions. A weak one asks the model to compensate for the machinery around it.

Frontier models

The model can often compensate for harness limitations. Differences still matter, but they may be incremental.

Mid-tier models

Tool design, prompt discipline, and context selection begin to decide whether a task stays on track.

Free-tier models

A good harness helps turn limited quotas and uneven capability into useful, bounded work.

Local models

Every token and tool call matters. The surrounding system can be the difference between a demo and a daily driver.

This is why Pi can be especially useful with smaller models: it gives you a minimal base that is easy to shape. But Pi alone is not the entire solution. A limited local model may also need focused components such as Little Coder to constrain the coding loop, package context carefully, and make edits easier to complete. The winning setup is not necessarily one product. It can be a composition.

Add components at the level where they belong

Claude Code can be paired with DeepSeek and local models. OpenCode and Pi can span frontier providers, free tiers, and local runtimes. That is only the base. The next layer is the context and components you add around them.

Project components belong to a particular codebase: repository instructions, architecture notes, project-specific skills and context, build commands, and conventions. Global components belong to you: reusable preferences, roles, skills and context, credentials, and harness configuration supplied through a user home. The working directory tells the agent which project to operate on; the components tell it how to work there. One project can demand a cautious migration specialist while your global setup still carries the same review habits and tool preferences everywhere you work.

The combinations are already multiplying

Once harnesses, models, project components, and global components are independently configurable, you no longer have a simple model leaderboard. You have hundreds of possible agent configurations. That is good news: you can optimize for privacy, cost, latency, capability, or all four. It is also an evaluation problem. Which harness makes your local model useful? Does a project skill improve the result, or does it only sound good in its own description? Did a new global role help consistently, or did the model simply get lucky on this run?

The useful comparison is not model versus model. It is complete agent configuration versus complete agent configuration, including a blank baseline.

Always keep a blank-config baseline

If you built a skill, test it against the same harness and model with no skill installed. If you created a model home, compare it with a clean project context. Keep the task, repository state, and acceptance criteria fixed. Change one layer at a time when you want to understand causality; change the whole stack when you want to choose the best daily setup.

  1. Choose a real, bounded task with a result you can inspect.
  2. Create named agents for each harness, model, project-component, and global-component combination.
  3. Include one blank configuration as the control.
  4. Run from equivalent repository states and give every agent the same prompt.
  5. Compare the code, tests, completion rate, corrections, tokens, cost, and elapsed time.
  6. Repeat across several tasks before promoting a configuration to your default.

The important word is frictionlessly. If every experiment requires rebuilding config files, opening more terminals, copying context, and manually recording usage, you will stop experimenting. You will settle on the setup that felt good once and call it the best.
