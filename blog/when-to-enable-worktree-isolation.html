When to enable worktree isolation

Sometimes you want several agents making independent changes as fast as possible. Other times you're editing alongside an agent, pulling in teammates' changes, and resolving conflicts. Those workflows need different boundaries.

Squid's worktree.enabled setting controls per-turn code isolation. In releases after 0.1.6, it defaults to false. Enable it deliberately when the benefit of private turn directories outweighs the extra integration step after each response.

This is the companion to What happens when two agents edit the same line, our earlier explanation of isolated turns and conflict handling. That post covers how isolation works; this one covers when to use it.

What the switch changes

With isolation enabled, each turn edits a private snapshot of the configured code roots. When the turn finishes, Squid merges its edits back into the backing checkout. Independent changes can come together cleanly; overlapping changes can require conflict recovery.

With isolation disabled, agents edit the configured code roots directly. There is no automatic per-turn promotion back to another directory. You work with the files the agents are changing, including during normal Git operations.

WorkflowStarting choice
Solo repo, independent agent tasks, backing checkout stays stableConsider enabling isolation
Frequent manual edits, rebases, or conflict resolutionKeep isolation off
Team repo with frequent upstream integrationKeep isolation off; separate feature checkouts
Several topics editing the same checkout directlySeparate the checkouts or serialize writes

Enable it for a burst of independent changes

A personal repository is a good candidate when you want an agent to update documentation, another to fix a parser, and another to add a separate UI component. Private snapshots keep each turn's in-progress edits apart. You can get several changes moving without giving every task a permanent checkout.

The cost comes when those snapshots return. Each response adds an integration step. If you also edit the backing checkout, change its history, or resolve a merge while turns are running, their starting snapshots can drift from the files they need to merge into. Even a solo repo can hit conflicts when tasks overlap.

During that burst, let active turns finish and their changes sync before doing manual integration work. An editing turn in an isolated directory cannot also perform the normal Git check-in workflow there; Git-only work happens against the backing repo after synchronization. Isolation suits a stable backing checkout and tasks with clear boundaries.

Leave it off when integration is part of daily work

If your day includes frequent rebases, hand edits to resolve conflicts, and incorporating teammates' changes, per-turn promotion adds another moving part. Turning isolation off lets you and your agents use the actual checkout throughout that work, without a second copy being merged back after every response.

That is why off is the default. Team size is a useful signal, but the deciding factor is how often the checkout changes underneath active turns. A solo developer doing frequent manual integration may also prefer it off.

Direct writes still need coordination. Wait for active writers before rebasing or resolving conflicts in their checkout. Turning isolation off removes Squid's promotion step; it does not make simultaneous edits to the same files safe.

Keep parallelism with a checkout per feature topic

You can keep isolation off and still run features in parallel. Give each feature topic its own persistent checkout directory and branch, then point that topic's code roots at its directory. You manage those checkouts explicitly; disabling per-turn isolation does not create them automatically.

#login topic   →  /projects/app-login   →  login feature
#search topic  →  /projects/app-search  →  search feature

             Separate directories, separate branches
             Integrate each feature when ready

A Git worktree is one way to maintain these directories without full clones. This is different from Squid's per-turn isolation: the feature checkout persists across turns, and you choose when to integrate its changes. One shared directory with branch switching cannot isolate concurrent topics, because switching changes the files for everyone using that directory.

Parallelism is now across topics: login and search can progress independently. Within one topic, agents still share that topic's files. Give concurrent writers separate file ownership or run their edits sequentially; reviews and read-only investigation can run alongside them. Topic per feature is a useful boundary, not automatic isolation for every agent in it.

You still need to integrate feature branches and resolve genuine conflicts. The difference is that integration happens at a deliberate feature boundary rather than after every agent response.

Choose the setting

In ~/.squid/squid.yaml, use direct writes:

worktree:
  enabled: false

Or opt into per-turn isolation:

worktree:
  enabled: true

Let active turns and any pending sync or conflict recovery finish before switching. Restart Squid after editing the configuration.

Upgrading from 0.1.6 or earlier

The new default applies to releases after 0.1.6. Upgrading does not automatically rewrite your existing configuration:

  • enabled: true stays enabled.
  • enabled: false stays disabled.
  • If worktree.enabled is omitted, Squid uses the new default, false.

That last case changes behavior on upgrade even though the config file is untouched. If you previously relied on the enabled default and want to keep isolation, set worktree.enabled: true explicitly before upgrading.

Start with isolation off for an interactive development workflow. Enable it when you want a controlled burst of independent agent edits. For ongoing parallel features, a persistent checkout per topic gives you a clear place to edit, review, and integrate each feature.
