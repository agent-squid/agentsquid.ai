Use the expensive model only when the work is expensive

The best coding model is not always the right model for the next prompt. Frontier models are valuable when a task is ambiguous, architectural, or genuinely difficult. But summarizing a completed diff does not need the same reasoning budget as designing it. Neither does preparing a commit message, checking routine changes, or handling the final push.

AgentSquid lets frontier, mid-tier, free-tier, and local models work in one workspace. Each can have its own named agent and session while sharing the same project history. You choose the level of capability the current step deserves instead of paying the frontier rate from beginning to end.

Frontier

Architecture, difficult debugging, risky refactors, and decisions with expensive consequences.

Mid-tier

Ordinary implementation, follow-up fixes, tests, and reviews after the hard decisions are made.

Free-tier

Useful overflow when a paid quota runs out or a bounded task does not justify another premium turn.

Local

Frequent mechanical work: summarize changes, draft handoff notes, prepare commit text, and push completed work.

Quota exhaustion should be a route change, not a dead end

When a frontier quota runs out, explicitly move the next turn to a mid-tier or free-tier agent. The work does not need to stop, and you do not need to pretend every model is interchangeable. The frontier model can make the hard decision; a less expensive model can carry out a well-bounded continuation.

This also works before the quota reaches zero. Squid exposes usage and quota signals so you can decide when the remaining work no longer deserves premium tokens. Switching models becomes a deliberate budgeting decision rather than an emergency after a provider rejects the next request.

Routine work belongs on hardware you already own

A local model can handle many repetitive end-of-task chores. For example, Qwen 3.5 9B Q4 can run on a Mac mini M4 with 16 GB of memory and take care of summarizing changes or completing a routine push workflow. It will not replace a frontier model on every coding task. That is not the point. It only needs to be capable enough for the work you hand it, and local tokens do not consume a hosted-model quota.

Pin context like adding items to a shopping cart

Changing models usually creates a context problem: the new agent needs to know what you asked, what the previous agent answered, and which files changed. In Squid, pin those responses and send the next prompt to the new model. The pinned user prompt, response, and changed-file context travel with the handoff.

Think of pinned context as a shopping cart. Add only the pieces the next agent needs, then carry that cart to another model. If an item is already present in that agent's session, Squid does not inject it again.

That gives you a practical middle ground between rebuilding context by hand and sending the entire history to every model. A local summarizer may need the original request, the final implementation response, and the changed files. A mid-tier reviewer may need those plus the test results. The cart can be small because the next job is small.

Yes, this is manual—and that is the control

Some people will say that nobody should route work by hand in the era of autonomous agents. If you have unlimited tokens and want the system to choose everything, that can be a great experience. But autonomy is not free when its decisions are paid for with a quota you cannot see disappearing.

As a cost-conscious user, I do not want to waste tokens without knowing where they went. I want automation where it removes drudgery and a visible decision where capability and cost change. Choosing a frontier model for the hard part, a mid-tier model for the continuation, and a local model for the cleanup is not micromanagement. It is resource allocation.

One workspace makes that allocation cheap. The models can change while the project, the evidence, and your control stay in one place.
