Two coding agents are better than one opinion

A coding agent can give you a confident answer, a clean diff, and a passing test suite. That still leaves a useful question unanswered: would another agent have made the same tradeoffs? The easiest way to get a second opinion is no longer to finish with one model, close the terminal, and reconstruct the whole problem somewhere else. Put both agents in the same workspace and ask them at the same time.

In Squid, an agent is more than a model name. It is a named configuration of coding harness, provider, model, working directory, and user home. That means two agents can look at the same project while keeping their native sessions, credentials, context, and preferences distinct. Their responses and changed files arrive together, where you can compare the reasoning and the actual implementation without tab archaeology.

Compare work, not benchmark trivia

Public benchmarks are useful, but they cannot tell you which agent understands your repository, follows your conventions, or handles the kind of ambiguity your team creates. A side-by-side run turns your real task into a small, relevant evaluation. Broadcast one prompt to two agents, then inspect both the answer and the files each one changed.

One agent may find the smaller fix while another catches the missing migration. One may write the stronger test but touch too much code. Sometimes they converge, which is evidence of a straightforward solution. Sometimes they disagree, which is exactly where a second opinion earns its keep. The goal is not to crown a universal winner; it is to see which approach is better for this job and why.

The same model can disagree with itself

Model-versus-model is only one experiment. Create two agents backed by the same model and give them different personas through separate user homes or role instructions. Make one a conservative maintainer who minimizes the diff. Make the other a skeptical reviewer who hunts for edge cases, security gaps, and missing tests. Because the model stays fixed, the comparison shows what the role, context, and instructions changed.

A useful pairing: ask the builder to implement the feature, then ask a fresh reviewer persona to challenge the result.

Measure the hidden difference: consumption

Quality is only half the comparison. Squid attaches usage to each prompt, including input and output tokens, cache behavior, reasoning tokens where the provider exposes them, cost, and duration. The analytics view rolls those numbers up by agent and topic, so repeated side-by-side runs reveal patterns that a single session total hides.

You may discover that one agent spends more tokens up front but needs fewer correction turns, while another is terse yet repeatedly reloads context. Squid's real-time quota tracker adds the operational view: you can watch how quickly each model consumes its available quota while the work is happening, instead of learning only when a provider limit interrupts the next prompt.

A simple comparison loop

  1. Create two named agents pointed at the same codebase, changing only the variable you want to compare.
  2. Broadcast the same bounded prompt to both as fresh turns so neither inherits an accidental advantage.
  3. Compare their explanations, changed files, tests, and assumptions side by side.
  4. Check per-prompt analytics and quota movement, then record which tradeoff mattered for the task.
  5. Repeat across several real tasks before deciding which agent should be your default.

The interesting question is rarely “Which model is best?” It is “Which agent, with which persona and context, gives me the best result at an acceptable cost for this kind of work?” A shared workspace makes that question cheap enough to ask every day.
