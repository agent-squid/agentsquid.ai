What happens when two agents edit the same line

Squid makes it easy to have several agents working the same repo at once — a session turn ticking along in one lane, a couple of adhoc side-quests firing off !, maybe a prompt broadcast sending the same message to several agents at once on purpose. Sooner or later, two of those turns touch the same file. This post covers what Squid actually does about that, and how to deliberately trigger a real conflict so you can watch the machinery work.

The failure mode this replaces

Without isolation, two turns writing to the same file at the same time isn't a Git operation — it's just two processes racing to overwrite the same bytes on disk. There's no three-way merge and no conflict marker, so whichever write lands last quietly wins. This isn't hypothetical: it's exactly what happened before Squid's per-turn isolation shipped — a change was silently overwritten by another parallel prompt's output, with no diff, no warning, and nothing surfaced anywhere to say it had happened. That's strictly worse than an ordinary merge conflict. A conflict at least tells you something collided.

Every turn gets its own copy of the repo

When a turn starts, Squid builds its private directory in three steps. First it checks out the repo at HEAD as the starting point. Then it overlays whatever's currently sitting uncommitted in repo_root — not just this turn's edits, but everything earlier turns already promoted and you haven't committed yet, since that's ordinary dirty working-tree state as far as Git is concerned. Only after that does it symlink in dependency and cache directories (node_modules, .venv, and friends) so tools still work without a fresh install per turn. The result lands under ~/.squid/worktrees/<repo>/sqd-<turn>/, and it has no .git of its own — it isn't a real Git worktree from the agent's point of view, just a plain folder — so there is nothing in it to git branch, push, or open a PR from, even by accident.

That means a turn never sees just "the last commit." It sees the last commit plus every uncommitted change accumulated so far, which is exactly what makes chaining turns feel continuous: ask one agent to add a function and a second, unrelated adhoc turn to fix a typo elsewhere, and both see each other's uncommitted work stacked on top of HEAD, even though each edits its own private copy and neither can see the other while it's still running. The agent is the sole writer to its own directory for the entire turn, no matter how many other turns are in flight against the same repo at the same time.

Merging back is a real three-way merge

When the turn ends, Squid snapshots that private directory and merges it into the repo's current state inside a disposable, Squid-only "integration worktree" — never in your actual working tree. Git does the real work of the merge, so two turns that touched different lines of the same file, or different files entirely, combine automatically, exactly like merging two branches would. Only overlapping lines produce an actual conflict.

A clean merge gets patched into your real repo as an ordinary, uncommitted file change — not a new commit. There's no per-turn commit trail to squash later; git status and git commit behave exactly as if you'd made the edit yourself. Your branch only moves when you actually ask for it — there's no special command for that either. A plain prompt like "push these changes" or "publish this" is enough; Squid recognizes it as a Git-only turn and runs it straight against the real repo.

The one rule: a single turn is either editing files or running Git history/remote commands against the real repo, never both. If you ask for an edit and a push in the same breath, Squid makes the edit, leaves it uncommitted, and tells you to ask again to actually publish it — it won't push in the same turn a file changed. Ask a second time with nothing left to edit and it goes straight through as a Git-only turn.

When lines actually collide

If the merge can't be resolved automatically, your real working tree is left completely untouched. The integration worktree is kept around with Git's actual conflict markers in it, and the conflicting file list shows up in the UI on the turn that hit the collision. From there you get three ways out:

  • Auto-Resolve — dispatches a follow-up turn scoped to that same integration worktree, handed a structured summary of the base content, the repo's current content, and the turn's own output for each conflicted file, so a model resolves it instead of you.
  • Resolve — open the conflicted file (still sitting with real <<<<<<< markers in the integration worktree), edit it by hand, then click Resolve to promote your fix back to the repo.
  • Discard Turn — drop this turn's pending changes entirely. Anything other turns already synced to the repo is untouched; only this turn's contribution disappears.

Whichever path you take, nothing lands in your real repo until the conflict is actually gone.

Set up a throwaway repo

Don't point this at anything you care about. A fresh, disposable repo makes the collision obvious and costs nothing to throw away afterward: 

mkdir -p /tmp/conflict && cd /tmp/conflict
git init -q
git commit -q --allow-empty -m init
printf 'foo = 0\n' > notes.txt
git add -A && git commit -q -m seed

That's an empty initial commit plus one seed commit adding notes.txt with a single line, foo = 0. Now start a new topic in Squid — #conflict works fine — and when it prompts for a code root, type /tmp/conflict. That prompt is where the code root actually gets set: it's stored in the topic's own memory, not the agent, so every agent you address through #conflict shares the same root.

It has to be a Git repo. Everything in this post — the private per-turn directory, the off-repo merge, the conflict itself — is Squid using Git as the merge engine, so a code root Git doesn't track can't get any of it. Point a topic at a plain, non-Git folder and turns fall back to editing it directly: no isolation, no turn-scoped diff, and two overlapping turns can silently overwrite each other with nothing surfaced — the exact failure mode this post opened with.

Trigger one yourself

The isolation only produces a visible conflict when two turns are genuinely running at the same time against the same starting point and edit the same lines. A normal session lane won't do it — turns to the same #topic@agent queue and run one after another. Adhoc turns are the way in: each ! turn gets its own ephemeral worker and starts immediately, with no queueing behind the session or behind each other.

The cleanest way to fire two of those from a single message is prompt broadcast (,): list more than one agent with no operator between them and Squid sends the literal prompt to each one independently and unwrapped, with no chaining between them at all — the same feature behind sending one question to Claude, Codex, and Cursor Agent at once for comparison.

#conflict@claude!,@claude! change foo in notes.txt to a random number and show the number in your response.One message, one topic, the same agent fired twice as two independent adhoc origins.

That's the extreme case, and it's actually the easiest one to reproduce: you don't need two different agents or two differently worded instructions. Both turns get the exact same prompt, but each independently picks its own random number for foo, so they're guaranteed to disagree on that same line without you having to hand-craft conflicting edits. Swap in a second agent (#conflict@claude!,@codex!) if you'd rather watch two different backends collide instead of one agent racing itself.

Here's what happens next:

  1. Both turns check out the repo's current state into their own private directory and start editing foo independently — neither can see the other's in-progress edit or its chosen number.
  2. Whichever turn finishes and syncs first wins cleanly. At that moment the repo hasn't changed since its turn started, so its number merges in with no conflict.
  3. The second turn syncs next, and now the repo's current content already differs from what it started from — on the very same line it also touched. Git can't reconcile that automatically, so this turn is the one that reports the conflict.
  4. The file stays exactly as the first turn left it. The conflict lives in the second turn's integration worktree until you resolve it.

Edit two different lines instead of the same one and you'll see the other half of this story: both turns merge in cleanly, no conflict at all, because Git only refuses to auto-merge when both sides touched the same lines.

This covers the behavior you'll actually run into. For the full mechanics — hidden snapshot commits, drift detection, promotion rollback, and why an earlier branch-based design got scrapped after an agent pushed an internal worktree branch to a real remote — see ADR-0025.
